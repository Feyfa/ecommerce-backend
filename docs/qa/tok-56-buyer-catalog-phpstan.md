# TOK-56 Buyer Catalog PHPStan Debt QA

## Purpose

This document tracks two related changes delivered under TOK-56.

The first change removes nine PHPStan findings previously assigned to
`BelanjaController` and `BuyerProductSearchService`. It declares the
authenticated local user and narrows Eloquent relation, price, timestamp, and
configuration values without changing the buyer catalog API or Meilisearch
document contract.

The second change replaces the Faker-based placeholder identity in
`PaymentService` with a static synthetic profile set and moves
`fakerphp/faker` from `require` to `require-dev`. This change was added to
TOK-56 after the staging deployment failed twice while downloading the Faker
archive during the production `composer install` layer of the backend image.

Implementation branch: `task/jd-tok-56`.

Status legend: ✅ verified, ⬜ not verified yet.

## Implementation Contract

### Buyer catalog

- The `/belanja` endpoint continues to use the local user installed by the
  required `auth.api` middleware as the buyer excluded from catalog results.
- Company name remains the preferred store name, with seller name and then an
  empty string as the existing fallbacks.
- Product price remains projected as an integer without adding a global model
  cast.
- Nullable Eloquent timestamps retain their ISO 8601 and Unix timestamp
  representations.
- Meilisearch fields, eligibility, filters, sorting, pagination, and API
  responses remain unchanged.
- Configured pagination limits and index names retain their existing scalar
  normalization.

### Payment placeholder identity

- `generateFakeUser()` keeps its `status` and `user` return shape, including
  the `name`, `email`, `phone`, and `address` keys, and now declares them as a
  complete array shape instead of a loose string map.
- The profile is selected at random from ten static sandbox profiles, so the
  endpoint keeps returning a non-deterministic placeholder name.
- `/api/payment/account/validate` retains its existing response contract of
  `status` and `username`, along with every preceding authorization,
  empty-account, slug, and duplicate-account branch.
- The `?? ''` fallback in `PaymentController` was removed because the declared
  array shape makes `name` always present. This is a type-contract alignment,
  not a behavior change.
- `fakerphp/faker` moved to `require-dev` at the same resolved version
  `v1.24.1`. It is retained rather than deleted because `UserFactory` still
  calls `fake()`.
- No other dependency was upgraded, and `composer.lock` was regenerated by
  Composer rather than edited by hand.
- The endpoint still returns a placeholder name only; it performs no real bank
  account-holder verification. That pre-existing limitation is unchanged.

## Known Limitations

- `composer format:check` cannot start under the default PHP 8.5 installation
  because the Homebrew build is missing `libnetsnmp.40.dylib`. The same Pint
  entry point was executed directly with PHP 8.3 instead, and it passed.
- Only the success path of `/api/payment/account/validate` is covered. The
  unauthorized, empty-account, empty-slug, unavailable-slug, and duplicate-
  account branches remain untested. They are pre-existing behavior that this
  task did not touch, and they are left as follow-up coverage rather than
  widening TOK-56 further.
- `PaymentServiceTest` establishes full profile coverage by repeating a random
  draw rather than by injecting a seed, because the generator uses
  `array_rand` directly. Three hundred draws make a missed profile
  vanishingly unlikely, but the guarantee is statistical rather than
  structural. Making it structural would require exposing the profile list,
  which would change the service API.

## Release Status

No migration, environment-variable addition, frontend change, or external API
contract change is required. The dependency change does affect the backend
Docker build, which is the intended outcome: the production `--no-dev` install
no longer downloads `fakerphp/faker`.

Jira TOK-56 remains In Progress. Commit, push, CI, the staging integration
branch, and the staging redeploy are outside the current local-validation
scope and are handled manually.
